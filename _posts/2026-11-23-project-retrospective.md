# 회고록

## 1. 활동을 돌아보며

나는 지금까지 칠보페이와 아두이노 RFID UID 인식기라는 두 가지 프로젝트를 진행했다.

칠보페이는 학교 생활에 포인트 시스템을 도입하기 위한 서비스 개발 프로젝트였으며, 아두이노 RFID UID 인식기는 RFID 모듈을 활용해 등록된 카드를 구분하는 하드웨어 프로젝트였다.

두 프로젝트는 사용한 기술과 목적이 달랐지만, 공통적으로 처음 구상했던 기능을 실제로 동작하는 결과물로 구현하는 경험을 할 수 있었다.

처음에는 목표로 했던 기능을 구현하는 것 자체에 집중했다. 하지만 프로젝트를 마무리하고 돌아보니 단순히 작동하는 결과물을 만드는 것과 완성도 높은 시스템을 만드는 것에는 차이가 있다는 생각이 들었다.

이번 회고에서는 각 프로젝트를 진행하면서 부족하다고 느꼈던 부분과 앞으로 보완하고 싶은 점을 정리해 보려고 한다.

## 2. 칠보페이 프로젝트

### 2-1. 기능 구현에 집중했던 개발 과정

칠보페이는 QR 코드를 활용한 포인트 적립부터 포인트 관리, 상품 교환까지 하나의 서비스 안에서 구현하는 것을 목표로 했다.

프로젝트를 진행하면서 가장 중요하게 생각했던 부분은 기획했던 기능을 실제로 동작하게 만드는 일이었다. 화면을 구성하고 서버와 연결하며 사용자가 서비스를 이용하는 전체적인 흐름을 구현하는 데 집중했다.

하지만 기능이 정상적으로 작동하는지만 확인하다 보니 실제 사용 환경에서 발생할 수 있는 여러 상황을 충분히 고려하지 못했다는 아쉬움이 남았다.

예를 들어 사용자가 같은 QR 코드를 반복해서 인식하거나, 네트워크 오류로 요청이 중복 전송되는 경우에는 어떻게 처리해야 할까? 포인트를 차감하는 도중 오류가 발생한다면 데이터는 어떤 상태로 남아야 할까?

이러한 예외 상황을 충분히 고려하지 못했다는 점이 아쉬웠다.

앞으로는 기능을 구현하기 전에 정상적인 사용 흐름뿐 아니라 예상할 수 있는 예외 상황까지 먼저 정리하고, 각각의 상황에 대한 처리 방식을 설계하는 습관을 들여야겠다고 생각했다.

### 2-2. 데이터 관리와 보안에 대한 부족함

프로젝트를 진행하면서 데이터 관리와 보안에 대해서도 더 깊이 고민할 필요성을 느꼈다.

특히 포인트는 사용자에게 실질적인 가치를 제공하는 데이터이기 때문에 단순히 숫자를 증가시키거나 감소시키는 방식으로 관리해서는 안 된다.

포인트가 적립되거나 차감될 때마다 누가, 언제, 어떤 이유로 포인트를 사용했는지 기록하는 거래 내역 관리가 중요하다. 또한 중복 요청이나 비정상적인 접근으로 인해 포인트가 임의로 변경되지 않도록 서버 측 검증과 권한 관리도 필요하다.

개발 당시에는 기능이 정상적으로 작동하는지에 집중했지만, 실제 서비스에서는 사용자가 전달하는 데이터를 무조건 신뢰해서는 안 된다는 점을 더 중요하게 생각했어야 했다.

앞으로는 데이터의 무결성을 유지하는 방법과 인증 및 권한 관리, 서버 측 검증 방식 등을 공부하고 실제 프로젝트에 적용해 보고 싶다.

### 2-3. 실제 서비스 운영에 대한 고려

칠보페이는 단순한 개발 연습용 프로그램이 아니라 실제 학교 생활에서 활용하는 것을 목표로 했던 프로젝트였다.

그렇기 때문에 기능 구현뿐 아니라 실제 사용 환경에서 발생할 수 있는 문제도 고려했어야 했다.

사용자가 서비스를 처음 접했을 때 쉽게 이해할 수 있는지, 운영자가 데이터를 효율적으로 관리할 수 있는지, 문제가 발생했을 때 원인을 파악하고 복구할 수 있는지 등을 충분히 고민할 필요가 있었다.

또한 사용자가 늘어났을 때 서버가 안정적으로 동작할 수 있는지, 데이터가 손실되었을 때 복구할 수 있는지 등 운영 측면의 고려도 부족했다.

앞으로는 단순히 개발을 완료하는 것에서 그치지 않고, 서비스를 배포한 이후의 유지보수와 운영까지 개발 과정의 일부로 생각해야겠다고 느꼈다.

## 3. 아두이노 RFID UID 인식기 프로젝트

### 3-1. 동작 구현과 원리 이해 사이의 차이

아두이노 프로젝트에서는 UNO 보드와 RFID-RC522 모듈을 활용해 카드의 UID를 읽고, 사전에 등록된 UID와 비교해 등록 여부를 확인하는 프로그램을 제작했다.

처음에는 카드를 인식하고 시리얼 모니터에 결과를 출력하는 것만으로도 충분하다고 생각했다.

하지만 프로젝트를 마무리하면서 RFID 모듈이 데이터를 읽어오는 과정과 SPI 통신이 실제로 어떤 방식으로 동작하는지 충분히 이해했는지 돌아보게 되었다.

라이브러리에서 제공하는 함수를 사용하면 카드 인식이나 UID 읽기와 같은 기능을 비교적 간단하게 구현할 수 있었다. 하지만 각 함수가 내부적으로 어떤 과정을 수행하는지, RFID 모듈과 아두이노 사이에서 데이터가 어떤 방식으로 전달되는지에 대해서는 더 공부할 필요가 있었다.

앞으로는 라이브러리의 함수를 단순히 사용하는 데 그치지 않고, 내부적으로 어떤 동작이 이루어지는지 확인하며 개발하는 습관을 들이고 싶다.

### 3-2. UID 비교 방식과 데이터 처리의 한계

이번 프로젝트에서는 사전에 등록된 UID를 배열에 저장하고, 새롭게 인식된 UID와 비교하는 방식으로 등록 여부를 판단했다.

기능 자체는 간단하게 구현할 수 있었지만, 등록된 카드가 많아지는 상황을 생각하면 현재 방식에는 한계가 있다고 느꼈다.

등록된 UID를 코드 내부에 직접 작성하는 방식은 새로운 카드를 추가하거나 기존 정보를 변경할 때마다 코드를 수정하고 다시 업로드해야 한다.

또한 UID의 길이가 카드마다 다를 수 있다는 점도 고려해야 한다. 실제 구현에서는 특정 길이의 UID를 기준으로 비교했기 때문에 다양한 UID 길이를 가진 카드를 지원하려면 비교 로직을 개선해야 한다.

앞으로는 UID를 별도의 데이터 구조로 관리하거나, EEPROM과 같은 비휘발성 메모리를 활용해 등록 정보를 관리하는 방법도 시도해 보고 싶다.

### 3-3. 실제 인증 시스템으로 발전시키기 위한 고민

이번 프로젝트는 등록된 UID인지 확인하는 간단한 인증 기능을 구현했다는 점에서 의미가 있었다.

하지만 실제 출입 통제나 사용자 인증 시스템에 적용한다고 생각하면 추가적으로 고려해야 할 부분이 많았다.

가장 먼저 UID만으로 사용자를 안전하게 인증할 수 있는지 고민해 볼 필요가 있다. UID는 카드의 식별 번호이기 때문에 이를 확인하는 것만으로 강력한 보안성을 보장할 수는 없다.

실제 서비스에서는 카드 복제나 UID 위변조 가능성 등을 고려해야 하며, 필요한 경우 별도의 인증 절차와 보안 기능을 함께 적용해야 한다.

또한 현재는 시리얼 모니터에 결과를 출력하는 방식이었지만, 실제 시스템이라면 LCD나 LED, 부저 등을 활용해 사용자가 인증 결과를 직관적으로 확인할 수 있도록 개선할 수도 있다.

처음에는 단순한 카드 인식 기능으로 시작했지만, 실제 환경에서 활용하기 위해서는 하드웨어 구성과 보안, 사용자 경험까지 함께 고려해야 한다는 점을 느꼈다.

## 4. 앞으로의 개선 방향

두 프로젝트를 진행하면서 각각 다른 부족함을 느꼈지만, 공통적으로 결과물을 만드는 데 집중한 나머지 그 결과물이 실제 환경에서 어떻게 활용될 수 있을지 충분히 고민하지 못한 부분이 있었다.

앞으로 프로젝트를 진행할 때는 다음과 같은 점을 보완하고 싶다.

- **기초 원리 이해:** 사용하고 있는 라이브러리와 기술이 내부적으로 어떤 방식으로 동작하는지 이해하기
- **체계적인 설계:** 구현에 앞서 데이터 구조와 시스템의 전체적인 흐름을 먼저 설계하기
- **예외 상황 고려:** 정상적인 동작뿐 아니라 오류와 비정상적인 입력에 대한 처리 방식도 구현하기
- **보안 의식:** 사용자 데이터와 시스템의 무결성을 유지하기 위한 보안 요소를 개발 초기부터 고려하기
- **테스트와 검증:** 기능이 동작하는 것에 만족하지 않고 다양한 상황에서 안정적으로 작동하는지 확인하기
- **확장성 고려:** 현재의 기능뿐 아니라 추후 기능 추가와 유지보수가 쉬운 구조로 개발하기

## 5. 마무리

이번 두 프로젝트는 서로 다른 기술과 환경에서 개발을 경험해 볼 수 있었다는 점에서 의미가 있었다.

칠보페이를 통해 하나의 서비스를 기획하고 여러 기능을 연결하는 과정에서 데이터 관리와 보안, 운영의 중요성을 느꼈으며, 아두이노 프로젝트를 통해 하드웨어와 소프트웨어가 연결되는 과정과 기술의 내부 동작을 이해하는 것이 중요하다는 점을 알게 되었다.

무엇보다 이번 활동을 통해 단순히 원하는 기능을 구현하는 것만으로는 충분하지 않다는 사실을 느꼈다.

어떤 기술을 사용했는지뿐 아니라 왜 그 기술을 사용했는지, 어떤 문제가 발생할 수 있는지, 더 나은 방법은 무엇인지 고민하는 과정이 필요하다고 생각한다.

앞으로도 다양한 프로젝트를 경험하면서 부족한 부분을 발견하고, 이를 하나씩 보완해 나가고 싶다. 단순히 동작하는 결과물을 만드는 데 만족하지 않고, 그 결과물의 원리와 구조까지 이해하며 더 나은 시스템을 설계할 수 있는 개발자로 성장하고 싶다.
